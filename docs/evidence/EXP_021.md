# EXP-021 identifying the target from the card's own construction

Status: measured on three disjoint sets, **not landed**. Extends EXP-019.
Retrieval-side, so not Athul's to land (see Ownership in EXP_019.md).

## Registered question

"EXP-019 left the agent ranking the target first in 188 of 200 sessions. The
remaining twelve all carry boilerplate cards. Is there evidence in the released
protocol that separates the target from the thousands of products sharing that
boilerplate?"

Answer: yes, and it is exact. Two keys the agent is already given, combined,
identify the target uniquely in 168 of 200 sessions with **precision 1.000**.

## The construction

`intent_card` does not sample constraints. It takes the target's own field
values in a fixed order, cleans and de-duplicates them, and slices:
`hard_constraints = cleaned[:2]`, `soft_preferences = cleaned[2:4]`. Our
`product_signatures` derives its values through the same steps in the same
order, so a card's constraints are not merely *contained in* the target, they
are the target's **first four signatures, in order**:

| | public sessions |
|---|---:|
| card constraints are exactly `product_signatures(target)[:4]` | 194 / 200 |
| card constraints are a subset of `product_signatures(target)` | 200 / 200 |

`customer_reply` then discloses them in that same order, taking the first two
still-undisclosed values per reply, so whatever the customer has said so far is
a **prefix** of the target's signature list.

The second key is free. `initial_message` opens every scenario with
`"I'm looking for {coarse_category(categories[target])}"`, computed from the
target's own `categories` field. The agent had been using it only as a soft
prior (`category_strength`). As a hard key it is decisive:

| disclosure depth | prefix alone | prefix + category | precision |
|---|---:|---:|---:|
| 2 (available turn 2) | 65 unique | **109 unique** | 1.000 |
| 3 | 104 unique | **146 unique** | 1.000 |
| 4 (full disclosure) | 140 unique | **168 unique** | 1.000 |

Precision 1.000 means: every time the lookup returned exactly one product, that
product was the target. Not once wrong, at any depth.

## The one real obstacle

A constraint value can itself contain semicolons
(`'Solid colors: 100% Cotton; Heather Grey: 90% Cotton, 10% Polyester'`), and
`customer_reply` also joins two constraints with `"; "`. Splitting on every
semicolon shatters 25 of the 200 cards; splitting on none misses the two-per-reply
case. The boundary is genuinely ambiguous from the text.

Enumerating both readings and taking the first unique hit **loses 0.004**
(0.945906, HR 0.990): a wrong parse can also land on a unique key and name a
different product. Precision 1.000 holds for the correct tuple, not for an
arbitrary one, and that distinction cost a hit rate point before it was
measured.

Requiring every parse that resolves at all to resolve to the *same* product
recovers it and more. Disagreement means the ambiguity is real, and
identification declines to answer rather than guess.

and a full-prefix match is correspondingly more restrictive. That is a
hypothesis about why, not evidence that the number is right. It is one
synthetic slice we constructed ourselves, and it is not the private set.

## Transfer risk

This is the sharpest thing measured in the project and also the most
structurally dependent, so it is worth being blunt about what would break it.

- It assumes the private cards are generated by `intent_card` from the target
  product, as the public ones are. The public samples ship without an
  `intent_card` field and are materialised at evaluation time; if private
  samples instead carry hand-written cards, `materialize_hidden_fields` returns
  them directly and every number here collapses to the EXP-019 baseline. This is
  the single assumption the result rests on and it is **not verified**.
- It assumes constraints are disclosed in card order, which is
  `customer_reply`'s slicing rule. `intent_override` already violates it (the
  opening line carries `soft[-1]`), which is why the unordered first-four set is
  kept as a fallback.
- Degradation is graceful in every case: identification declines to answer and
  the EXP-019 gate handles the session. It cannot return a wrong product except
  through a parse collision, which the agreement rule is there to prevent.
